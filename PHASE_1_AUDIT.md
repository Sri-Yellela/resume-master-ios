## ⛔ Constraint violation in the README — fix before anything else

The README documents:

> **Hard throw right: immediate apply**

**A gesture must NEVER submit an application.** Applications reach real employers under the user's
real name and cannot be recalled. Every safeguard in this system — semi mode, the provenance
overlay, four independent pre-submit gates, and the product's printed promise *"nothing is submitted
until you approve it"* — assumes a human reviews first. A hard throw is the easiest gesture on a
phone to fire by accident.

**In the Android repo this was implemented in FIVE places, not one**, and reached a user-facing
confirmation that lied:

| # | Location | Was |
|---|---|---|
| 1 | `README.md` | `Hard throw right: apply` |
| 2 | `models/SwipeAction.kt` | `data object Apply` |
| 3 | `ui/jobs/CardStackLayout.kt` | `if(ax>HARD_OFFSET) SwipeAction.Apply` |
| 4 | `ui/jobs/SwipeOverlay.kt` | overlay read `"APPLY NOW"` in green with a check |
| 5 | `ui/jobs/ActionBadge.kt` | badge read **`"Application sent"`** — for 2.5 seconds, having sent nothing |

**#5 is the one to note.** The view model already routed `Apply` into the same local queue list, so
the app told users it had applied on their behalf when it had not — a surface reporting an
irreversible action it did not perform.

**Trace the equivalent in this repo and report every occurrence.** Velocity may still distinguish a
stronger signal, but **the stronger signal must also only queue** (queue-and-prioritise). Android
resolved this as `QueuePriority` doing `queue.add(0, job)`.

Also check any badge or toast copy promising unattended submission — Android's "Queued for
auto-apply" became "Queued for review" for the same reason.

## The other three constraints

**1. GENERATION IS DEFERRED TO APPROVAL, not queue time.** Each resume generation costs ~$0.04 and
swiping is ~1s per job, so five idle minutes is ~60 jobs / ~$2.40 from a gesture costing no thought.
Right-swipe must cost nothing. The backend enforces `APPLY_DAILY_QUEUE_CAP` (40) as a **typed
response field** (`DailyCap` / `QueueCap` schemas) carrying `limit` and `remaining` — render
`remaining`, never swallow it.

**2. GATED JOBS CANNOT BE COMPLETED ON A PHONE.** `automationTier` `gated` / `account` (Workday,
Meta, Amazon) requires a desktop browser extension borrowing the user's authenticated portal session
under a per-gesture `activeTab` grant. There is no extension on iOS. **Note `unknown` is also
`completableOnMobile: false`** — broader than "gated". Either filter server-side via
`tiers_include`/`tiers_exclude` or show "finish on desktop"; never queue them into a state the phone
cannot resolve.

**3. ELIGIBILITY ANSWERS ARE NEVER GESTURED.** Work authorisation, sponsorship, years of experience
and custom answers are attestations to an employer. Stored profile only.

### 3 · Screen inventory

Every screen: what it is, its state source, and whether it is wired or static.

Android had **13 screens, 0 wired to a server** — everything from `MockData.kt`, every mutation

### 4 · Networking — the critical question

Android had **no HTTP client** (no Retrofit, OkHttp or Ktor) plus one hand-rolled
`HttpsURLConnection` call with **zero callers**, which would have failed anyway.

Report whether this app has any API layer, or renders local/mock data. If there is none, that is the
largest single gap and it sizes everything else.

### 5 · Auth — ⛔ the credential distinction that trips people

```
POST /api/auth/login         -> authContext   SESSION-BOUND. DO NOT PERSIST.
GET  /api/auth/mobile-token  -> token         sessionLess, durable. THIS is the credential.
```

A login-issued token stores `session_sid = req.sessionID` and is swept by
`revokeBrowserAuthContexts`; the mobile mint stores NULL and that sweep deliberately never touches
it. **Persisting the login token produces intermittent, untraceable sign-outs.**

Flow: login → `GET /api/auth/mobile-token` → persist in the **Keychain** (never `UserDefaults`) →
`Authorization: Bearer` thereafter. Idle 7d sliding, absolute 90d.
`POST /api/auth/revoke-mobile-token` for sign-out.

Report what this app does today. Android had **no auth of any kind** — no login screen, no token
storage, nothing to violate yet. Also check for a `YOUR_DOMAIN.com`-style placeholder base URL;
Android had one in its LinkedIn manager and its deep-link host while using the real domain
elsewhere.

### 6 · The API contract

`../draft/contract/mobile-api.v1.json` — v1.1.0, 29 paths, 48 schemas. Note `contract/` is
**gitignored** as a generated artifact, so `git ls-files` will not find it; look on disk.

Report whether it is vendored here and what it specifies for auth, the Job shape including
`automationTier`, cursor pagination, queue/approve, and the Auto Apply feeds.

Things it flags that an unaware client walks into:

- **Eight fields have no null coalescing server-side**, so `JSON.stringify` **deletes** them — they
  arrive **absent, not null**. A Swift `Decodable` throws on a missing key it would happily accept
  as `nil`. The contract types them optional; honour that.
- **Use cursor paging, not offset.** Offset silently skips rows the user swiped away — measured at
  6 of 25 with 3 swipes per page. Cursors are valid only for the filter set that produced them.
- **Use `/api/jobs/interact`, not `PATCH /api/jobs/{id}/starred`** — the latter **toggles**, so a
  retried swipe on a flaky network undoes itself and returns 200.
- `sourcePlatform` is a trap; it looks like the ATS name and is not. Use `automationTier`.
- `x-retired` lists five endpoints answering 410. *"A greenfield client written from older
  documentation is precisely the client that will call these."*
- `CHECKSUMS.json` hashing is **LF-normalised on purpose** — the desktop repo runs
  `core.autocrlf=true` while the mobile repos are CRLF. A raw-byte verify here fails spuriously.

### 7 · Local model vs server shape

Android's hand-rolled parser read **snake_case** against a **camelCase** server, so five fields
failed silently to `nil` — salary never rendered, tags always empty, remote never labelled. Its
`Job` model carried **10 fields against the server's 37**, with `matchScore` hardcoded to 0 despite
the server providing a real value.

Compare this app's models field by field against the contract and report every mismatch.

### 8 · Persistence

Android's resume builder was **in-memory only** — process death lost every edit. Invisible while
data is mock, real data loss the moment it is not. Report what persists here and what does not.

### 9 · Admin surfaces

Android shipped **6 admin screens of fabricated data, ungated** (no auth existed to gate against),
with Delete / Suspend / Impersonate controls that looked functional and hit nothing. Recommendation
there is a build flavour, not deletion, and **not shipped in a store build**.

Report whether any equivalent exists here. Do not build it, do not delete it — flag it.

### 10 · README accuracy

Report **every** claim the code does not support. Android's list included "full admin panel"
(6 mock screens), "Swipe-card job feed" (10 hardcoded fixtures), and "Velocity-sensitive card stack"
— which was false: the resolver read displacement, never velocity, and `MIN_VELOCITY` was declared
and never referenced.

The iOS README also links `resume-master-web` with a **`YOUR_USERNAME` placeholder**. The real repo
is `github.com/Sri-Yellela/draft`.

### 11 · Store readiness

Signing, bundle identifier, provisioning, App Store Connect state, and the **App Store privacy
manifest**. What exists, what is missing.

The privacy declaration must be authored against the live policy at `https://jobsviadraft.com/privacy`
and must not contradict it. Note the app collects nothing today (no network reaches the server), but
Phase 2 introduces email, name, work authorisation and resume content.

## Phase 2a — after Phase 1 is accepted

Order will be: **toolchain → auth → contract-typed API layer (incl. `automationTier`) →
persistence.** No feed. See `../draft-android/PHASE_2A.md` for the sibling's version.

The **review queue is the product's promise**, not a secondary screen — a user who swipes 40 and
reviews 0 has spent money and applied to nothing. Its endpoints already exist:
`GET /api/apply/pending` (*"the review inbox"*), `POST /api/apply/approve` (*"THE moment of
submission"*), `POST /api/apply/reject`, `GET /api/apply/questions`, `POST /api/apply/answers`,
`GET /api/apply/readiness`.
